-----------------------------------------------------------------------------------------
source: NWS (api.weather.gov)	
-----------------------------------------------------------------------------------------
Two calls per US city:

1. Station lookup → /points/{lat},{lon} — finds the nearest ASOS weather station and returns the URL for that station's hourly forecast

2. Hourly forecast → the returned forecastHourly URL — fetches all hourly temperatures for the target day, takes the max as μ, estimates σ from the diurnal spread

This is the fallback when NOAA NBM is unavailable. Blended in at 20% weight.

-----------------------------------------------------------------------------------------
source: Open-Meteo Ensemble (ensemble-api.open-meteo.com)	
-----------------------------------------------------------------------------------------
One provider, three separate endpoints — no API key required (free, no auth):

1. ECMWF ensemble → ensemble-api.open-meteo.com/v1/ensemble with models=ecmwf_ifs04
The 51-member ECMWF IFS forecast. This is the primary forecast input.

2. GFS ensemble → same endpoint with models=gfs025
The 31-member NOAA/GFS forecast. Secondary forecast input, blended 35% with ECMWF.

3. ERA5 climatological archive → archive-api.open-meteo.com/v1/archive
10 years of historical observed temperatures used to build the climatological prior. Cached in SQLite after the first fetch.

So "OpenMeteo" in your .env is actually doing the heaviest lifting — it's the source of all three ensemble model runs and all historical climate data.

-----------------------------------------------------------------------------------------
source: NOAA CDO (ncdc.noaa.gov)	
-----------------------------------------------------------------------------------------
This is the National Blend of Models text product. Not a REST JSON API — the bot scrapes a plain-text formatted bulletin from NOAA's MDL (Meteorological Development Laboratory) server.

The bulletin contains Q10/Q25/Q50/Q75/Q90 temperature quantiles for a given ASOS station, updated several times daily (the bot tries forecast cycles 12z, 06z, 00z, 18z in order).
From those 5 quantiles the bot derives μ (= Q50) and σ (= IQR / 1.349).

This is the primary US supplemental source. Blended at 30% weight when available. Preferred over NWS hourly because it gives explicit uncertainty quantiles rather than a single point forecast.

-----------------------------------------------------------------------------------------
source: Tomorrow.io (api.tomorrow.io) | https://docs.tomorrow.io/reference/welcome
-----------------------------------------------------------------------------------------
Sanity check only — not used in the blend. The bot fetches temperatureMax for the target day and compares it to the blended μ. If the deviation is >5°C it logs a warning, but it doesn't change the forecast or block the trade. If the API returns a 429 (rate limit), the bot sets a flag and skips all further Tomorrow.io calls for that scan cycle.

Q: How is this information used to ultimately make a decision?

    A:
    ensemble_p = Σ(source_probability × brier_weight) / Σ(brier_weight)
    disagreement = stdev([p1, p2, p3, p4])  # if > 0.15, skip the contract

    The result is a single probability (0–1) representing the ensemble's best estimate of whether the weather event occurs.

#########################################################################################

Q: What Are the Weather APIs Actually Returning?

    A:
    The APIs return raw forecast values (temperatures in °C, precipitation in mm). They do not return the probability of reaching a specific threshold. Your bot must compute that probability itself.

    Here is what each source actually provides and how it becomes a probability:
    Open-Meteo Ensemble — 39 independent model runs ("members")
    Each member is a separate simulation of the atmosphere with slightly different starting conditions. The ensemble API returns 39 separate temperature or precipitation forecasts:

    temperature_2m_max_member01: [19.8°C]
    temperature_2m_max_member02: [22.4°C]
    temperature_2m_max_member03: [20.1°C]
    ... 39 members total

    The contract asks: "Will Shanghai reach 29°C or higher?"

    Your bot computes: P(temp ≥ 29°C) = members_above_29 / 39

    If 7 of 39 members forecast ≥ 29°C: prob = 7/39 = 0.18

    "How often has Shanghai hit 29°C+ on April 9 in the last 10 years?"
    → 6 out of 10 years → historical_prob = 0.60
    This is a climatological prior — it tells you what's normal, not what tomorrow's weather will be. It carries the lowest weight (0.15) for this reason.

    The Full Picture:

    Contract: "Will Shanghai reach 29°C or higher on April 9?"
    threshold = 29.0°C

    Open-Meteo ensemble  → 39 member forecasts → P(any member ≥ 29°C) = 0.18  weight 0.35
    NOAA historical      → 10yr base rate      → P(historical ≥ 29°C) = 0.60  weight 0.15
    NWS                  → US only, skip       →                              weight 0.00
    Tomorrow.io          → tempMax = 24.2°C   → soft prob via delta formula   weight 0.10

    ensemble_p = (0.18×0.35 + 0.60×0.15 + soft×0.10) / (0.35 + 0.15 + 0.10)
            = weighted average = ~0.31

    market_p = 0.43  (Polymarket YES price)
    edge     = 0.31 - 0.43 = -0.12  → bet NO`

Q: What is ERA5?

    A: ERA5 — "ECMWF Reanalysis v5." It's a global historical weather dataset produced by the European Centre for Medium-Range Weather 
    Forecasts (the same organization that runs the main ensemble model). It works by taking all available historical observations 
    (weather stations, radiosondes, satellites) and running a climate model backward over them to produce a physically consistent, gap-free 
    reconstruction of atmospheric conditions back to 1940.  When you ask "what was the actual high temperature in London on April 10, 2019?" 
    — ERA5 is the authoritative answer. It's essentially the gold standard for historical weather data.

#########################################################################################

Q: What is KDE?
    
    A: KDE — "Kernel Density Estimation." It's a statistical technique for estimating a probability distribution directly from data, without 
    assuming any particular shape. A normal distribution forces your data into a bell curve defined by just two numbers (mean and standard deviation). 
    KDE instead places a small "kernel" (a smooth bump) at each data point, then sums all the bumps together to form the overall distribution. 
    The result can capture shapes a normal distribution can't — like a slight left skew, a fat tail, or a subtle bimodal pattern. For temperature, 
    most city/date combinations are approximately normal so the difference is small, but for cities with more complex seasonal patterns it can 
    meaningfully improve accuracy.

    your USE_KDE_CLIM feature flag controls the shape of the distribution fit to historical data, not bias correction. These are two separate things:

    USE_KDE_CLIM — switches the climatological prior from a normal distribution (parametric, described by μ and σ) to a KDE (nonparametric, described by the data itself). This affects the shape of the distribution used to compute bin probabilities
    Bias correction (bias.py) — a completely separate adjustment applied to the ensemble forecast mean (μ). It answers the question: "historically, when ECMWF says London will be 12°C on an April day, is it actually 12°C, or is it systematically off by +1°C or −0.5°C?" It corrects the forecast center before computing any probabilities
    The relationship between them:


    Raw ECMWF ensemble  →  bias correction applied  →  corrected μ
                                                            ↓
    Historical ERA5 data  →  KDE or normal fit  →  climatological prior
                                                            ↓
                        Bayesian blend of corrected forecast + prior
                                                            ↓
                            P(temp in bin_i) for each outcome range

Q: What occurs in the "DISCOVERY RUN" loop?

    FREQUENCY: Runs every 4 hours at the top of the hour. 12am, 4am, 8am, etc.

    A: Single responsibility: find what markets exist. Occurs every 4 hours.

    1. Calls Polymarket Gamma API (/events?tag_slug=temperature) — paginated, ~2 pages × 100 events = ~200 API calls with the 1 req/s rate limiter
    2. For each event, normalizes the sub-markets (parses temperature ranges, extracts city/date/lat/lon)
    3. Returns the event list — nothing is written to the DB here
    
    External API calls made: Polymarket Gamma API only. ~2-5 calls for the happy path (tag slug works), up to ~60 calls on the fallback full scan.

#########################################################################################

Q: What occurs in the "TRADING RUN" loop?

    FREQUENCY: Runs hourly at 10 minutes past the hour. 12:10am, 1:10am, 2:10am, etc.

    A: For each discovered event (say there are 20 active markets). Occurs every 30-60 minutes.

        Step	            What happens	                    APIs called
    Weather fetch	    ECMWF ensemble	                    Open-Meteo Ensemble API (1 call/event)
                        GFS ensemble	                    Open-Meteo Ensemble API (1 call/event)
                        ERA5 climatology	                Open-Meteo Archive API (cache miss only)
                        NOAA NBM (US)	                    NWS Points + MDL NBM text product (2 calls/US event)
                        Tomorrow.io	                        Tomorrow.io API (1 call/event, skipped if rate-limited)
                        Bias correction	                    SQLite only — no API
    Edge calculation	Kelly sizing, signal generation	    No API
    DB write	        Persist events + outcomes	        SQLite only
    Execution	        Place orders (if signals pass risk)	Polymarket CLOB API

    For 20 events: ~40-60 weather API calls per trading run. The ERA5 calls are heavily cached after the first run so most of those go to SQLite. Tomorrow.io rate-limits itself after the first few calls per cycle.

#########################################################################################

Q: What occurs in the "MONITOR RUN" loop?

    FREQUENCY: Runs hourly at 30 minutes past the hour. 12:30am, 1:30am, 2:30am, etc.

    A: The settlement loop is deliberately lighter than the trading loop — it doesn't call weather APIs at all. Its main cost is a handful of 
    Gamma API calls (one per open position to check resolution status). With 5-10 open positions at a time, that's 5-10 API calls per settlement 
    run, well within any rate limit. Occurs every 1-2 hours. 

    1. Cancel pending orders — any live order not filled before this run is cancelled via CLOB API, logged with cancelled_reason="unfilled_before_monitor_run"
    2. Settle resolved markets — checks Gamma API for each open position; if closed=True, determines winner from outcomePrices, computes P&L, marks position closed. For live trades, prefers cashPnl from the Polymarket Data API (on-chain source of truth) over our own math
    3. Update unrealized P&L — refreshes current_price and unrealized_pnl for all open positions (Data API for live, Gamma API for paper)

UPDATES / DETAILS:

1. Exit position logic/position monitoring - 
-----------------------------------------------------------------------------------------
> This is a gap in the current code. There is no position monitoring loop. Polymarket weather contracts are binary and self-resolving — when the resolution date passes, the contract settles at 1.0 (YES wins) or 0.0 (NO wins), and your USDC is returned automatically on-chain. The bot doesn't need to send an exit order.
> update_position_outcome() in db.py exists to record the exit price, exit time, and P&L
> This function is not used yet, nobody calls it — there is no resolver/monitor loop that checks contract outcomes and updates the DB. This is a missing piece.

Short answer: positions are not monitored after entry. There is no loop, scheduler job, or resolver that:

Checks whether a contract has resolved
Reads the final outcome from the CLOB API
Calls update_position_outcome() to close the position in the DB
What exists:

get_open_positions() in db.py — fetches all status='open' rows (used by risk.py for exposure calculations)
update_position_outcome() in db.py — ready to close a position given exit_price, exit_time, pnl
get_open_orders() in execution.py — fetches live orders from CLOB API
What's missing: a resolver.py or scheduled job that polls open positions, checks Polymarket for resolution status, and calls update_position_outcome(). This is the next critical feature to build.

2. Additional statistical analysis with stored data:
-----------------------------------------------------------------------------------------
> Three are genuinely valuable for this use case:

> Warming trend correction — London's April 10 max temperature has risen ~0.3°C/decade due to climate change. Without detrending, the climatological prior is biased cold. A simple linear regression over stored historical values detects and removes this bias before computing μ and σ
> ECMWF bias correction — After each Polymarket contract resolves, store (forecast_mu, actual_tmax). Over time, you'll detect systematic biases (e.g., ECMWF runs 1.2°C warm in Bangkok in April). Apply city+month-specific corrections to future forecasts. This is proven operationally at NCEP/ECMWF
> KDE for non-normal distributions — Some cities have bimodal April temperature distributions (e.g., continental cities where either a warm front or cold front dominates). KDE fits these better than a normal distribution and gives more accurate bin probabilities

ML Stack Build-Out — Reference Summary
Background and goals
The original trading bot priced Polymarket weather contracts using an ensemble of physics-based forecasts (ECMWF, GFS, ERA5 climatology, NWS hourly), converted blended μ/σ predictions into per-bucket probabilities via a Gaussian CDF, and bet using fractional Kelly sizing. The goal of this work was to add an independent, observation-driven machine learning layer that could complement the physics ensemble — particularly for same-day predictions where current observations contain information the morning forecast hasn't captured. The strategic intent was three-fold: (1) give the bot a second opinion on each event so we can size up when ML and ensemble agree, (2) help discriminate between two bins when the market is split, and (3) give us early warning when a held position's underlying probability is changing before market price reprices. We deliberately built this as shadow infrastructure first — predictions are computed and persisted but ML_BLEND_WEIGHT_MAX=0.0 keeps them out of trade decisions until we've validated the model in production. The user is currently running the market_price_value strategy, so the ML hooks were specifically wired to surface bin probabilities on MPV events without changing how MPV trades.

What was built
We started by expanding the Visual Crossing API integration to capture a much richer feature set per pull (dew point, pressure, visibility, wind gust/direction, solar radiation, snow, UV index, etc.) and added the corresponding columns to live_observations so every 20-minute scan now persists 12 additional weather variables. We then built the shared feature vector pipeline (bot/ml/features.py + schema.py) which is the single source of truth for what features exist and in what order — used by both training (over historical backfill rows) and live inference (over current DB state) so they can never drift. The v1.0 schema captured 27 features (temporal cyclical encodings, current observations, recent trajectory deltas, year-over-year T_max lags), and we later upgraded to v2.0 with 19 additional features including derived quantities (morning heating rate, dew-point-depression-based T_max proxy, clear-sky GHI integration, insolation efficiency), climatology anomaly z-scores (pressure/dew/cloud/wind expressed as standard deviations from the city's per-doy-per-hour normal), an inversion-suspect flag, and 8 static city descriptors (elevation, latitude, hemisphere, coastal flag, Köppen-zone one-hot). To support the anomaly features we built the climatology builder (bot/scripts/build_obs_climatology.py) which aggregates ~440K (city, day-of-year, hour) bucket means/stds and ~18K (city, day-of-year) daily T_max statistics from 10 years of historical data — these now live in the obs_climatology_hourly and obs_climatology_daily tables and double as both ML inputs and a free climatology baseline for any other risk/sanity logic.

We then built the historical backfill pipeline (bot/scripts/backfill_training_data.py) which walks every (city, year, month) in a 10-year window, fetches from Visual Crossing (or our newly-added on-disk cache), and assembles training rows by computing feature vectors at 10:00, 12:00, and 14:00 local time on each day with the actual T_max from VC as the label. This produced ~547,000 training rows across 50 cities at v2.0. The VC disk cache (bot/data/vc_cache/) is critical infrastructure — it's now populated to ~6,150 month-files (2.4 GB) so all future feature iterations cost zero queryCost. We trained two model architectures: the v1 TempDistributionModel (one per city, predicts μ via HistGradientBoostingRegressor and σ via per-month residual standard deviation) which gave us a median RMSE of ~1.34°C across 50 cities, and the v2 PooledQuantileDistributionModel (single model for all cities using city as a native categorical plus the 8 static city features, predicting 7 quantiles {q5, q10, q25, q50, q75, q90, q95} via separate quantile-loss HGBRs) which improved median RMSE to 1.19°C with empirical-CDF bin probabilities (no Gaussian assumption) and 75.9% empirical coverage of the 80% prediction interval (slightly under-confident, conservatively safe). The pooled model especially helped historically hard cities (Mexico City 2.36→2.01°C, Dallas 1.93→1.54°C, Denver 1.91→1.63°C, Chicago 1.81→1.63°C) by learning universal feature relationships from 547K rows instead of 7K per city.

The inference pipeline (bot/ml/inference.py) loads the pooled model once per process, manages caches for timezones and per-city climatology lookups, builds a live ctx dict from the latest live_observations row plus historical T_max lookups, and exposes two public APIs: get_ml_distribution() returning (μ, σ, model_version, decision_hour metadata) and get_ml_bin_probabilities() returning normalized empirical-CDF bin probabilities for any list of (low, high) ranges. Two gates protect inference: it only fires for target_date == today (D=0) and only when local time at the city is between 09:00 and 17:00 (within ±3 hours of the trained 10/12/14 folds — outside that window we'd be extrapolating). The actual current local hour is used for the model call (cyclical hour features handle interpolation between trained folds); the closest fold is logged separately as a diagnostic. This inference is already wired into weather.py as a fourth blended source for the top_bin_value strategy, but ML_BLEND_WEIGHT_MAX=0.0 means it logs predictions to decision_snapshots.ml_mu_c/ml_sigma_c without affecting the blended μ/σ. For the market_price_value strategy, we lifted the previous strategy gate so MPV scans now also compute ML predictions: after writing temp_outcomes for an event, MPV calls get_ml_bin_probabilities() on the event's bin list and bulk-UPDATEs each outcome row with ml_bin_prob, ml_decision_hour, and ml_model_version. Trade behavior is unchanged — these probabilities are persisted purely for dashboard display and future entry/exit logic decisions you'll design.

The dashboard was updated in three ways: each event card is now strategy-aware so MPV cards show the top-4 bins by market price (instead of incorrectly hiding them when model_prob is null); each card shows the city's local time in its header (e.g., "Local: Sat 17:08 CEST"); and for D=0 events during the inference window, an additional "ML Prob" column appears on cards and an "ML Bin Prob" column appears in the per-event modal — both auto-hide when no data is present. The evaluation script (bot/ml/evaluate.py) generates per-city markdown reports comparing the model's OOF predictions against actual T_max, against naive baselines (persistence, year-over-year, climatology day-of-year mean), and reports calibration (do residuals respect the predicted σ?) — this is how we'll know whether to eventually flip ML_BLEND_WEIGHT_MAX above zero.

New functionality you can leverage immediately
Single pooled model file at bot/ml/models/pooled_v2.0.joblib — handles all 50 cities, loads once per process, predicts μ/σ or full quantile distribution per city for any same-day event during 09:00–17:00 local
Empirical-CDF bin probability API — get_ml_bin_probabilities(city, lat, lon, target_date, event_id, bins) returns per-bin probabilities normalized to sum to 1 from a non-Gaussian distribution that respects skew (heat waves cluster in upper tail, cold pools clip lower tail)
Per-bin ML probability persisted on temp_outcomes for every D=0 event during MPV scans — three new columns: ml_bin_prob, ml_decision_hour (the closest trained fold 10/12/14), ml_model_version
MPV event cards now display bins (top 4 by market price), local time at the city, and an additional ML Prob column when same-day predictions exist — same visual experience MPV users get on top_bin_value cards
Free climatology lookups for any (city, day-of-year, hour) — usable beyond ML for risk filters, anomaly detection, "is this temperature unusual?" sanity checks
Per-city per-day-of-year T_max climatology with percentiles (p10/p25/p50/p75/p90) — usable as an entry-time filter ("market's #1 bin is outside historical p5..p95 → flag as extreme weather day")
Visual Crossing disk cache primed with ~6,150 month-files — every future feature iteration (v3, v4, …) costs zero queryCost; just edit features.py, bump FEATURE_VERSION, re-run backfill
Shared feature builder that backfill and inference both use — no train/serve skew possible
Calibrated quantile predictions — empirical 80% interval covers ~76% of actuals, 50% interval covers ~47% — close enough to honest that the σ is usable for Kelly sizing
Per-city evaluation reports in bot/ml/diagnostics/{city}_{date}_report.md showing RMSE, calibration, and naive-baseline comparison — the gate to deciding whether to ramp ML_BLEND_WEIGHT_MAX above zero
Two trained model architectures available — v1 per-city (50 files, simpler, weaker on hard cities) and v2 pooled quantile (1 file, stronger on every city, non-Gaussian); inference auto-prefers pooled when present, falls back to per-city if missing
Static city descriptor file (bot/ml/data/city_static_features.json) — elevation, Köppen zone, hemisphere, coastal flag for all 50 cities; usable beyond ML for any per-city categorization
Decision-time metadata logged with each ML prediction — actual decision hour, closest trained fold, model version — makes future debugging and A/B comparison clean
What's deliberately NOT yet enabled
ML predictions don't yet influence trade decisions (ML_BLEND_WEIGHT_MAX=0.0); they're persisted and displayed only
No conviction-based sizing multiplier wired into MPV entries
No ML-driven predictive exit (selling a bin before the market reprices when ml_bin_prob collapses)
No pair-switching exit (selling the disfavored bin when holding two and ML strongly prefers one)
No re-entry signal (re-buying after a stop-out when ML hasn't dropped)
These are the next layer of strategy logic that the user wanted to design themselves once the ML data substrate exists — which it now does.

Database evolution — what changed, what it enables
What the database tracked before today
Before this session, the database (signals.db) was built around capturing the current state of each trading cycle. The temp_events table stored one snapshot per event per scan — the blended forecast μ and σ, the climatological prior, days ahead, overround, and normalization warnings. The temp_outcomes table stored per-bin results: market price, model probability, edge, EV, Kelly size, and whether a signal was generated. The positions table tracked trades from entry to exit with price, P&L, and fill status. Supporting tables included era5_daily (historical climate cache), forecast_errors (bias correction pairs), historical_observed_daily (VC station observations for bias backfill), and historical_forecasts_previous_runs (Open-Meteo archived forecasts). There was also a legacy signals table retained for backward compatibility.

The fundamental limitation was that everything was point-in-time. The database could tell you what the model believed at the moment of a scan, but not how that belief evolved over the hours leading up to the scan. It couldn't tell you what the temperature was doing throughout the day, whether the forecast had shifted since the last pull, or what the world looked like at the exact moment a trade was entered. Every scan overwrote the previous context. If you wanted to know "what did the model think 4 hours ago for this same event," the data simply wasn't there.

What the database tracks after today
The database now captures change over time across four new dimensions.

First, forecast_runs and forecast_hourly store every ECMWF and GFS forecast pull as its own immutable row, tagged with event_id, source, and pulled_at timestamp. Each run links to up to 72 hourly temperature/humidity/cloud/wind/precip rows in forecast_hourly. Nothing is overwritten — every 2-hour pull produces new rows. This means you can reconstruct exactly what the forecast said at any point in the past, compute how much the forecast shifted between pulls (forecast drift), and measure whether models that shifted late were more or less accurate.

Second, live_observations stores a Visual Crossing observation every 20 minutes for each active event — current temperature, humidity, cloud cover, wind, precip, conditions, and the observed daily max so far. This is the intraday heartbeat of the system. It answers questions like "was the temperature rising or falling in the hour before we entered this trade?" and "at what point during the day did the observed max exceed our forecast?" The observed_max_so_far_c field on each row is what powers the distribution floor in the live adjustment layer — the hard constraint that the daily high cannot be less than what's already been measured.

Third, decision_snapshots captures the complete context at every trade evaluation, one row per bin per trading cycle. Each row stores the latest forecast run IDs (so you can join back to the exact forecast that was active), the latest observation ID, the blended and adjusted μ/σ, the live adjustment components as a JSON blob, the market price, model probability, edge, EV, recommended side, Kelly size, and now also the VC forecast diagnostic fields. This table is the single most important addition for trade analysis. It lets you reconstruct why any trade was entered, what the model believed at that exact moment, what the live adjustment was doing, and whether VC agreed or disagreed — all without relying on log files or timestamps that might not align.

Fourth, vc_forecast_diagnostics stores what Visual Crossing's own forecast said at each observation point — the projected daily high, the disagreement with our model in degrees and in bins, hourly-path RMSE, and warning flags. This is the shadow measurement layer that lets us evaluate whether VC forecast information has predictive value before we commit to using it in the model.

Supporting all of this, temp_events gained 14 new "current state" columns that serve as a fast-access cache — the latest forecast timestamp, latest observation timestamp, current temp, observed max, expected temp now, actual-minus-expected, forecast deltas, forecast agreement, adjusted μ/σ, live adjustment score, and components JSON. These columns are updated in-place on every observation and forecast loop so that dashboards and the trading engine can read the current state of an event with a single row lookup instead of joining across the time-series tables. The temp_outcomes table gained model_prob_blended (the pre-adjustment probability alongside the active probability) and several future-use columns for exit priority and fee-adjusted edge. The positions table gained entry_snapshot_id and exit_snapshot_id (linking trades to the exact decision context), entry-time forecast delta and actual-vs-expected, max favorable and adverse excursion fields, and an exit reason column.

A separate backtest.db file holds all backtest-specific data — historical hourly observations from the Archive API, empirical σ values derived from forecast errors, and the results of every backtest replay run. Keeping this separate means you can rebuild or purge backtest data without any risk to live trading state.

What this enables that wasn't possible before
The most immediate gain is the live adjustment layer — the system now uses intraday observations to dynamically shrink the forecast uncertainty (σ) as the day progresses and to truncate impossible outcomes below the observed max. This produced a 15% Brier score improvement in backtesting. That layer depends entirely on the new live_observations and forecast_hourly tables; without them, it would have no data to work with.

Beyond the live adjustment, the time-versioned architecture opens several future capabilities. Trade attribution becomes possible: you can join a closed position to its entry snapshot and exit snapshot and see exactly what changed between those two moments — did the forecast shift? Did observations diverge from expectations? Did VC start disagreeing? Forecast quality monitoring is now automatic: compare forecast_runs at different pull times against historical_observed_daily to track whether ECMWF or GFS is drifting in accuracy over weeks. Exit logic can be built on top of decision_snapshots by comparing the current snapshot to the entry snapshot — if the thesis has deteriorated (forecast shifted against the position, observed temp trending the wrong way, VC now disagreeing), that's a quantifiable exit signal. Position sizing refinement could use forecast_agreement_c (the gap between ECMWF and GFS) as a confidence modifier — when models agree closely, size up; when they diverge, size down. Intraday trend detection is possible from live_observations — three consecutive 20-minute readings showing accelerating temperature rise could be an early signal that the day will exceed forecast, useful for same-day contract entries.

The vc_forecast_diagnostics table specifically enables the evaluation of whether VC should eventually become a third forecast source in the blend, or whether it's more useful as a risk filter. Run python scripts/vc_diagnostic_report.py --days 14 after a couple weeks of data accumulation to see the analysis.

What didn't change
The core probability engine in weather.py — the ECMWF + GFS + climatology blend that produces the base μ and σ — was not modified. The live adjustment layer sits on top of it as an additive correction. The blending weights, the Bayesian blending schedule, the ERA5 climatological prior, the bias correction logic, the KDE option — all untouched. If you ever need to disable the live adjustment and revert to pure-blend behavior, setting USE_LIVE_ADJUSTMENT=false in .env returns the system to its pre-session state immediately. The new tables will continue to accumulate data (useful for later analysis) but the trading engine will ignore them.
